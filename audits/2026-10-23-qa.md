## Coverage, and what blocked it

- **Storefront:** covered. Home, services, service detail, barbers, book, walk-in queue, ticket lookup, appointment lookup, account sign-up and sign-in, account reset, 404, mobile menu, metadata.
- **Dashboard:** mostly blocked (see QA-002 and QA-003). The QA Admin sees zero shops, so every Shop workflow page shows an access error. Every model list page (`/dashboard/<list>`) crashes with a 404. That means I could not exercise services, staff, schedules, a booking, a check-in, POS payment or Store Settings editing.

"Get started" seeds a whole sample shop ("Full setup" or "Minimal setup") and has no shop-name field, so whatever it creates in production can't be labelled QA. That breaks the brief's data rule (see QA-012). Code check (`features/platform/onboarding/scripts/seedBarbershopDemo.ts:336-342`): it creates a new **private** shop when a public one already exists, so running it should not take down the live storefront. A fix session could run it with an owner-approved login to unblock dashboard QA.

## Blocker

### QA-001 — Online booking offers no times on any date (practitioner authority check rejects every slot)
- **Area:** storefront
- **URL:** https://openfront-barbershop-production.up.railway.app/book
- **Steps:** Open /book. Leave Classic Cut and First available selected. Try dates 2026-10-24, 10-26, 10-27 and 10-30, and also pick each single barber.
- **Expected:** open slots inside the published hours (for example, Tue 9:00 AM – 7:00 PM).
- **Actual:** "No times on this date." on every date, for every barber and every service. Nobody can book online. The public API confirms it: `checkBarberAvailability(barberId:"cmtygtqv60015ns3y6szunmf7", date:"2026-10-27", serviceDuration:35, serviceId:"cmtygtqe7000ans3yzzwtqooo", includeUnavailable:true)` returns every working slot with `available:false, blockedReason:"Practitioner authority unavailable"`. The rest are "Break time". `practitionerCredentials` returns `[]` for the admin session.
- **Likely files:** `features/keystone/queries/checkBarberAvailability.ts:61-67` calls `requireEffectivePractitionerAuthority`. `features/keystone/utils/practitionerAuthority.ts` and `localFixtureAuthority.ts` reject the seeded demo credentials ("Synthetic onboarding records are not practitioner authority"), or the production shop has none. The demo shop needs valid credential rows. Separately, a barbershop probably shouldn't hard-block every slot on a per-service credential row at all: one shop licence or barber licence is normal. Whatever the fix, when no slot is bookable for a credential reason, the storefront should explain why instead of saying "No times on this date".

### QA-002 — The admin login has no shop, so every Shop workflow page is locked
- **Area:** dashboard
- **URLs:** /dashboard/platform/booking, /queue, /barbershop, /services, /staff, /customers, /pos, /reports, /store-settings
- **Steps:** Sign in as the QA Admin and open each Shop workflows item.
- **Expected:** a global Admin can run the shop, or at least gets a working path to take over or join the existing shop.
- **Actual:**
  - Booking board: "Booking access restricted".
  - Walk-in queue: "You do not have access to the active shop queue".
  - Shop operations, Services & packages, Barbers & schedules: "Select exactly one active shop before performing this operation."
  - Customers and POS: "You do not have access…".
  - Reports: "Reports are temporarily unavailable."
  - Store Settings: "No active shop memberships."
  - The API agrees: `shops: []`, `shopMembershipsCount: 0`, `barbersCount: 0`, `servicesCount: 0`, even though the storefront shows 3 barbers and 6 services.
  
  The login was created by psql insert, without a ShopMembership. Even so, the product gives an Admin-role user no way to recover (no "claim shop", no membership UI that loads; see QA-003). Every error message also tells the user to "ask a shop owner or manager", and none exists that this user can reach.
- **Likely files:** shop-scoping in `features/platform/lib/*` and `features/keystone/utils/*` (the active-shop resolver). `features/keystone/models/ShopMembership.ts`. For the QA loop itself: add an owner ShopMembership for `qa@openship.org` on the demo shop.

### QA-003 — Every dashboard model page 404s, and the dashboard home says "No lists configured"
- **Area:** dashboard
- **URLs:** /dashboard (home), /dashboard/services, /barbers, /appointments, /practitioner-credentials, /barber-schedules, /products, /payment-providers, /users, /shops, /services/create
- **Steps:** Sign in, then open /dashboard, then any model list URL (paths taken from `adminMeta.lists[].path`). Separately, open Models in the sidebar.
- **Expected:** the home page shows model cards with counts, as in Openfront E-commerce. List pages render.
- **Actual:**
  - Home page: "No lists configured — There are no data models configured in your admin interface."
  - Every list page: HTTP 404, then the error boundary "Something went wrong", with console "Dashboard operation failed (details redacted)".
  - The Models sidebar group opens to nothing.
  - The same `KsFetchAdminMeta` query sent by curl with the same session cookie returns 200 with 47 lists. So the API works, and the **server-side** fetch fails. This hits every list, including `users` and `shops`, which are not shop-scoped, so it isn't the membership problem from QA-002.
- **Likely files:**
  - `features/dashboard/actions/getAdminMetaAction.ts` (`getCachedAdminMeta`). Its failure makes `HomePage` show the misleading empty state (`features/dashboard/screens/HomePage/index.tsx:80-90`) and makes `ListPage` call `notFound()` (`features/dashboard/screens/ListPage/index.tsx:33-35`).
  - `features/dashboard/lib/keystoneClient.ts` and `getBaseUrl.ts`: the server calls its own public URL via `x-forwarded-host`/`x-forwarded-proto` with `redirect:'error'`, which is worth checking first on Railway. The response is about 379 KB.
  - Also: the home page should show an error state, not "No lists configured", when the fetch fails.

## Major

### QA-004 — Deposit services can be picked on /book but can never be booked; there is no online payment
- **Area:** storefront
- **URL:** /book (Hot Towel Shave, Cut + Beard)
- **Steps:** On /book, choose Hot Towel Shave.
- **Expected:** either the deposit is taken (Stripe test mode, like E-commerce checkout) or the service is clearly marked "call to book" before it's picked.
- **Actual:**
  - The service can be selected, and the summary shows "Pay: Deposit $10.00".
  - The time list always says "No times on this date", because `checkBarberAvailability.ts:38` returns `[]` when `service.depositRequired`.
  - The service detail page does say "Online booking unavailable for deposit-required services", but /book never does.
  - There is no Stripe or online payment anywhere in the storefront (`grep -i stripe features/storefront` finds only CSS).
  - For a barbershop, deposits on long or premium services are day-one, and so is no-show protection.
- **Likely files:** `features/storefront/screens/BookingPage.tsx:325-335,416`, `features/keystone/queries/checkBarberAvailability.ts:38`. Payment sessions exist in the models (`PaymentSession`, `PaymentProvider`), but the storefront doesn't use them.
